# adjuntos-en-comentarios — Un comentario puede llevar un adjunto, y el que baja apunta a `files/`

**Estado:** Borrador · **Versión:** 0.1 · **Última actualización:** 2026-09-11

**Dónde cae.** Solo en `muckpile`.

---

## Contexto

**En Jira, un adjunto es siempre del ítem.** No existe un adjunto "del comentario": una imagen pegada en un comentario es un adjunto más en `fields.attachment`, que es de donde `pull` arma `files/`. Lo que el comentario tiene es una referencia a ese adjunto.

Medido el 2026-09-11, leyendo un comentario con una imagen que se pegó en el editor de Jira, y escribiendo en un ítem descartable de `ACC`, que después se borró:

| Qué | Resultado |
|---|---|
| Una imagen pegada en un comentario | Es un adjunto del ítem. El comentario la referencia con un nodo `media` de tipo `file`, cuyo `id` es de la API de media y no el del adjunto. |
| La relación entre el id de media y el del adjunto | La REST no la da: ni la subida de un adjunto ni su metadata devuelven el id de media. Solo el HTML la resuelve: `renderedBody` trae `<img src="…/rest/api/3/attachment/content/<id>">`. |
| Un comentario con `media` y el id del adjunto | 400, `ATTACHMENT_VALIDATION_ERROR`: Jira valida la referencia. |
| Un comentario con un link a `/rest/api/3/attachment/content/<id>` | Se acepta, y vuelve igual. |
| Un comentario con un link a `/secure/attachment/<id>/<nombre>` | Se acepta, y vuelve igual. |
| Un comentario con `media` de tipo `external` que apunta al adjunto | Se acepta, pero Jira lo muestra con un error: "Can only create thumbnails for attached images". |

---

## Decisión

### 1. `comment --attach <archivo>` sube el adjunto y lo linkea desde el comentario

**`--attach` sube el archivo al ítem, como `attach`, y agrega al final del comentario un link a `<base>/secure/attachment/<id>/<nombre>`**, con el nombre del archivo como texto. Se puede repetir, una vez por archivo.

- **No lo incrusta como imagen.** Incrustar pide el id de media, y la REST no lo da.
- **Sigue las reglas de `comment`, no las de `attach`:** va con `--ai` o `--i-human`, y lo gobierna `auto_comment` (la parte de `muckpile` de `decisiones-vivas`, § 2). El adjunto es parte de lo que dice el comentario.
- **El link es a `/secure/attachment/…` y no a la API** porque es la URL de descarga de la UI de Jira. Falta ver en el navegador que las dos abren el adjunto para una persona.

### 2. Un adjunto referenciado en un comentario baja como link a `files/`

**Al bajar un comentario, cada referencia a un adjunto del ítem pasa a un link markdown al archivo local:** `[captura.png](../files/captura.png)`. `thread/<id>.md` y `files/` son hermanos bajo `<id>_data/`.

- **Una referencia es cualquiera de estas dos cosas:**
  - un nodo `media` de tipo `file`, que se resuelve con el `renderedBody`. Se pide en la misma llamada de los comentarios, con `expand=renderedBody`, sin sumar requests;
  - un link a `/secure/attachment/<id>/…` o a `/rest/api/3/attachment/content/<id>` de este proveedor.
- **El nombre local es el de `files/`,** con el id adelante si hay dos adjuntos con el mismo nombre.
- **El nodo `media` se reemplaza por el link.** Un archivo de `thread/` es de solo lectura, así que no hace falta volver al ADF, y lo que importa es poder abrir el adjunto.
- **Una referencia que no se puede resolver queda como está:** un adjunto que el ítem ya no tiene, o un link a otro proveedor.

**Avance: 0/1.**
